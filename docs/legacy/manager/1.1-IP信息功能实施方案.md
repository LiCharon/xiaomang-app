# 1.1 IP 信息功能实施方案

## 1. 文档目的

本方案用于在 `ai-project-assistant-main` 中实现工作流第一步：

> 客户初步沟通内容信息 → IP 账号规划访谈信息采集清单（【1.1 IP 信息】）

该项目是客户信息的录入入口，负责将客户访谈资料整理、保存到 MongoDB；另一个项目 `xiaomang2` 负责读取数据库中的今日任务并继续执行账号定位、选题、文案和发布流程。

本次只实施“客户 IP 信息采集与管理”，不提前实现对标账号分析、选题库、黄金 3 秒、标题、结尾钩子或复盘功能。

## 2. 已确认的现状与约束

### 2.1 当前项目已有能力

- 服务端已经有 `Customer` 模型和客户 CRUD API。
- 客户模型当前使用扁平字段：
  - `name`
  - `occupation`
  - `contact`
  - `ipPositioning`
  - `contentNeeds`
  - `benchmarkAccounts`
  - `notes`
- 客户页面 `client/src/pages/CustomerList.jsx` 已支持客户新增、编辑、删除。
- 任务页面 `client/src/pages/TaskForm.jsx` 已支持选择客户，并把客户的基础信息带入任务。
- `xiaomang2` 当前依赖任务接口返回的扁平字段，例如客户名称、职业、联系方式、IP 定位、内容方向、对标账号、内容需求等。

### 2.2 必须保持的跨项目契约

1. 不删除或重命名现有 Customer 扁平字段。
2. 不改变任务接口中现有字段的含义和返回格式。
3. 新的结构化 IP 档案应作为增量字段加入，不能要求 `xiaomang2` 在本阶段同步改造后才能工作。
4. 任务创建时应保存一份 IP 档案快照，避免客户档案后续修改后，历史任务的上下文被悄悄改变。
5. AI 生成的内容只能作为草稿或建议，不能自动成为“已确认”的客户定位。
6. 缺失、冲突或低置信度的信息应标为“待确认”，不能静默丢弃。

## 3. 产品目标

完成后，项目经理可以：

1. 为客户录入初步沟通原始纪要。
2. 按采集清单逐项整理客户的身份信息、产品信息和用户画像。
3. 随时保存未完成的草稿，并看到采集完成度。
4. 在人工检查后确认当前版本的 IP 档案。
5. 在创建任务时复用客户档案，同时允许对当前任务做局部覆盖。
6. 让后续 `xiaomang2` 继续通过原有任务字段正常获取今日任务。

## 4. 建议的数据归属

### 4.1 客户档案放在 Customer 上

IP 访谈信息是客户级、长期复用的信息，不应只挂在某个今日任务上。因此建议在 `Customer` 中增加结构化字段 `ipProfile`。

任务只保存创建当时的 `ipProfileSnapshot` 和版本号。

关系如下：

```text
Customer
 └─ ipProfile（当前客户档案，可持续修订）

Task
 ├─ ipProfileVersion（创建任务时使用的版本）
 ├─ ipProfileSnapshot（创建任务时的快照）
 └─ 现有扁平字段（兼容 xiaomang2）
```

### 4.2 推荐的 Customer 字段

在不影响已有字段的前提下增加：

```js
ipProfile: {
  schemaVersion: { type: Number, default: 1 },
  status: {
    type: String,
    enum: ['draft', 'needs_review', 'confirmed'],
    default: 'draft'
  },
  profileVersion: { type: Number, default: 0 },
  interview: {
    rawNotes: { type: String, default: '' },
    source: {
      type: String,
      enum: ['client_interview', 'manual', 'imported'],
      default: 'client_interview'
    },
    completedAt: Date
  },
  identity: {
    name: String,                 // 姓名/昵称
    age: String,
    mbti: String,
    personaContrast: String,     // 人设反差点
    occupation: String,           // 职业身份
    yearsExperience: String,
    keyCases: String              // 关键项目/代表案例
  },
  product: {
    businessModel: String,
    productType: String,
    priceRange: String,
    coreAdvantages: String
  },
  userProfile: {
    gender: String,
    age: String,
    occupationIndustry: String,
    incomeLevel: String,
    consumptionHabits: String,
    consumptionScenarios: String,
    painPoints: String,
    goalsNeeds: String
  },
  updatedAt: Date,
  confirmedAt: Date,
  confirmedBy: { type: mongoose.Schema.Types.ObjectId, ref: 'User' }
}
```

说明：上面的字段是实现基线，不应被当作不可修改的最终清单。如果项目中已有正式版《IP 账号规划访谈信息采集清单》，应以正式清单的字段名称和分组为准，只需把数据映射到相同的存储职责中。

## 5. 采集清单与必填策略

### 5.1 建议分组

| 分组 | 采集内容 | 首次录入要求 |
| --- | --- | --- |
| 身份信息 | 姓名/昵称、年龄、MBTI、人设反差点、职业身份、从业年限、关键项目/代表案例 | 姓名/昵称必填，其余可选 |
| 产品信息 | 业务模式、产品类型、产品价格/区间、核心优势 | 可选 |
| 用户画像 | 性别、年龄、职业/行业、收入水平、消费习惯、消费场景、痛点、目标/需求 | 可选 |

### 5.2 完成状态

- `draft`：已创建或正在填写，尚未确认。
- `needs_review`：资料存在缺失、冲突或需要项目经理确认。
- `confirmed`：人工检查后确认，可以被后续任务默认引用。

空客户不建议额外持久化 `empty` 状态；前端根据 `ipProfile` 是否存在和完成度显示“未开始”。原始沟通纪要是输入留痕，不计入三组清单完成组数。

“保存草稿”不要求所有必填项完整；“保存并确认”需要通过必填校验，或由用户明确选择“标记为待确认”。

## 6. 推荐交互方案

### 6.1 客户列表页

改造 `client/src/pages/CustomerList.jsx`：

1. 增加“IP 档案”列，显示：
   - 未开始
   - 草稿
   - 待确认
   - 已确认
   - 当前版本号
2. 每个客户增加主操作“完善 1.1 IP 信息”。
3. 保留现有“编辑客户”操作，用于维护名称、联系方式等基础资料。
4. 在客户行上显示简短完成度，例如 `2/3 组已完成`，不要把整份档案展开在表格里。
5. 删除客户前继续保留确认提示；如果后续增加档案历史，删除策略要单独评估。

### 6.2 IP 档案编辑页

建议新增 `client/src/pages/IpProfileForm.jsx`，采用全页或宽抽屉，不建议继续把所有字段塞进现有窄客户抽屉。

页面结构：

```text
顶部：客户名称 / 当前状态 / 版本 / 完成度
主体左侧：姓名/昵称、联系方式、原始沟通纪要和补充说明
主体右侧：采集结果，默认展示关键字段；“更多信息”按身份信息、产品信息、用户画像分组展开
底部操作：保存草稿 / 标记待确认 / 确认建档
```

交互细节：

- “沟通纪要”使用大文本框，明确提示这是原始信息，不会被结构化整理覆盖。
- 每个分组标明“必填”和“可选”，并显示本组完成情况。
- 字段以简洁的单行或多行文本输入为主，不引入高密度标签和复杂表格。
- 离开页面或切换客户时，如果有未保存修改，弹出保存提示。
- 保存成功后保留当前步骤和滚动位置，避免长表单每次跳回顶部。
- 确认前检查原始纪要和姓名/昵称；用户点击确认后才更新状态并自动创建客户档案。
- AI 整理若实现，应使用“根据沟通纪要生成草稿”按钮，生成结果进入可编辑表单，并明确标注“AI 建议，需人工确认”。

### 6.3 客户选择与任务创建

改造 `client/src/pages/TaskForm.jsx`：

1. 客户选择后显示档案状态、完成度和版本。
2. 默认提供“使用客户 IP 档案”的开关，已确认档案默认打开；草稿或待确认档案默认提示用户检查。
3. 允许用户展开“本任务临时调整”，只覆盖当前任务，不回写客户档案。
4. 保存任务时同时写入：
   - `ipProfileVersion`
   - `ipProfileSnapshot`
   - 现有扁平字段
5. 将 `ipProfile.identity.occupation` 映射到任务的 `customerOccupation`；现有 `ipPositioning`、`contentDirection` 等旧字段继续沿用原客户字段，不把新的产品信息误映射为内容定位。

## 7. 服务端 API 设计

### 7.1 获取 IP 档案

```http
GET /api/customers/:id/ip-profile
```

返回：

```json
{
  "customerId": "...",
  "customerName": "...",
  "profile": {},
  "status": "draft",
  "profileVersion": 1,
  "completion": { "completed": 2, "total": 3, "percentage": 67 }
}
```

### 7.2 保存草稿或确认

```http
PUT /api/customers/:id/ip-profile
Content-Type: application/json

{
  "profile": {},
  "action": "save_draft"
}
```

`action` 建议支持：

- `save_draft`：保存内容，状态为 `draft`，不增加正式版本号。
- `mark_needs_review`：保存内容，状态为 `needs_review`。
- `confirm`：通过必填校验后保存，状态为 `confirmed`，版本号加一，并记录确认时间和确认人。

### 7.3 Customer CRUD 兼容策略

保留现有：

```http
GET    /api/customers
GET    /api/customers/:id
POST   /api/customers
PUT    /api/customers/:id
DELETE /api/customers/:id
```

现有接口继续接受原扁平字段。若编辑客户基础资料时带有旧字段，可同步更新 IP 档案中的对应字段，但不能用空字符串覆盖 IP 档案中已有的非空内容。

推荐映射：

| 旧字段 | 新字段 | 规则 |
| --- | --- | --- |
| `name` | `ipProfile.identity.name` | 仅当新字段为空时回填 |
| `occupation` | `ipProfile.identity.occupation` | 仅当新字段为空时回填 |
| `notes` | `ipProfile.interview.rawNotes` | 只做迁移时合并，不覆盖人工整理内容 |
| `ipPositioning`、`contentNeeds`、`benchmarkAccounts` | 无直接对应项 | 保留旧字段供旧任务链路读取，不在本阶段强行改写含义 |

### 7.4 任务创建接口

改造 `server/routes/tasks.js` 的创建逻辑：

- 如果带 `customerId` 且 `useCustomerProfile !== false`，读取客户当前档案。
- 将档案复制到 `ipProfileSnapshot`，并记录 `ipProfileVersion`。
- 从档案补全现有任务扁平字段；明确传入的“本任务临时调整”优先于客户档案。
- 客户没有档案时，继续使用现有扁平字段逻辑，不阻塞旧流程。

任务模型新增建议字段：

```js
ipProfileVersion: Number,
ipProfileSnapshot: mongoose.Schema.Types.Mixed,
ipProfileStatus: String
```

快照可以先使用 `Mixed`，但服务端应限制允许写入的结构和大小；不能直接把任意请求体永久写入数据库。

## 8. 数据迁移方案

新增幂等脚本，例如：

```text
server/scripts/migrate-ip-profiles.js
```

脚本要求：

1. 默认先 dry-run，输出将要更新的客户数量和字段摘要。
2. 只有 `ipProfile` 不存在或为空时才从旧字段回填。
3. 已有结构化档案不得被旧字段覆盖。
4. 从旧数据回填的档案状态设为 `needs_review` 或 `draft`，不能自动设为 `confirmed`。
5. 支持按客户 ID 或批次执行，便于异常恢复。
6. 执行前记录备份或明确的恢复方式。
7. 迁移后随机抽查客户，并确认旧字段仍可被任务接口返回。

建议执行顺序：

```text
1. 部署兼容模型和 API
2. 执行 dry-run
3. 备份数据库
4. 执行迁移
5. 抽查客户档案和任务创建
6. 再开放前端入口
```

## 9. 前端 API 封装

在 `client/src/services/api.js` 的 `customerAPI` 增加：

```js
getIpProfile: (id) => api.get(`/customers/${id}/ip-profile`),
saveIpProfile: (id, payload) => api.put(`/customers/${id}/ip-profile`, payload)
```

不要在组件中拼接 URL；所有新请求统一经过现有的 API 客户端和认证处理。

## 10. 鉴权、校验和安全

- 新的 IP 档案接口必须复用现有客户路由的认证中间件和权限规则。
- 客户档案中的联系方式、隐私和业务信息属于敏感业务数据，日志中不要打印完整内容。
- 服务端增加字符串长度、数组长度和数组项数量限制，避免超大请求写入 MongoDB。
- `profile.status`、`profileVersion`、`confirmedBy` 等系统字段不能由前端任意传入覆盖。
- `confirm` 必须由服务端重新执行必填校验，不能只相信前端校验结果。
- 对于并发编辑，至少增加 `updatedAt` 或版本检查；检测到版本变化时提示用户刷新，避免后保存者覆盖先保存者。

## 11. 实施顺序

### Phase 1：数据和兼容 API

1. 扩展 `server/models/Customer.js`。
2. 增加 IP 档案读写接口。
3. 增加字段清洗、权限和确认状态校验。
4. 扩展 `server/models/Task.js` 和任务创建逻辑，加入快照。
5. 编写迁移脚本并完成 dry-run。

### Phase 2：客户档案前端

1. 新增 `IpProfileForm.jsx`。
2. 在客户列表增加状态、完成度和入口。
3. 在 `App.jsx` 增加档案路由。
4. 在 `api.js` 增加封装。
5. 完成保存草稿、待确认、确认和离开提示。

### Phase 3：任务复用

1. 客户选择后读取并展示档案摘要。
2. 增加“使用客户档案”和“本任务临时调整”。
3. 创建任务时写入档案快照和兼容字段。
4. 验证 `xiaomang2` 今日任务数据无需改代码即可正常显示。

### Phase 4：可选 AI 整理

只有在人工表单和数据链路稳定后再增加。建议单独增加 AI 解析接口，不要让保存档案依赖 AI 服务可用性。

## 13. 验收标准

### 客户档案

- 新客户可以创建并进入“完善 1.1 IP 信息”。
- 原始沟通纪要可以单独保存，不会被结构化字段覆盖。
- 未完成资料可以保存草稿并重新打开。
- 缺失必填项时不能直接确认；用户可以标记为“待确认”。
- 确认成功后状态、时间、确认人和版本号正确保存。
- 刷新页面或重新登录后，档案内容和状态不丢失。

### 任务复用

- 选择客户后可看到档案状态和版本。
- 使用档案创建任务后，任务包含快照和版本号。
- 本任务临时调整不会修改客户的长期档案。
- 客户无结构化档案时，旧的任务创建流程仍能工作。

### 跨项目兼容

- `xiaomang2` 现有今日任务接口仍可获得 `customerName`、`customerOccupation`、`contact`、`ipPositioning`、`contentDirection`、`benchmarkAccounts`、`contentRequirements` 等扁平字段。
- 旧客户数据迁移后可以被正常读取。
- 新增字段不会导致旧任务页面报错。

### 验证命令和证据

目标项目至少应完成：

```bash
npm run build
```

同时进行一次真实或测试数据库的端到端验证：

```text
创建客户 → 保存 IP 草稿 → 重新读取 → 确认档案 → 创建任务 → 读取任务 → 检查扁平字段和快照
```

如果执行迁移，必须同时保留 dry-run 输出、迁移结果和抽查结果。没有这些证据时，只能报告“代码已修改”或“已定位”，不能报告完整功能已完成。

## 14. 本阶段明确不做的内容

- 不抓取对标账号。
- 不分析最近 60 条视频。
- 不建立口播类/演绎类选题库。
- 不实现黄金 3 秒、标题、结尾钩子库。
- 不实现发布仓和封面选择。
- 不实现周报、单视频复盘和选题配比学习。
- 不强制修改 `xiaomang2` 的现有页面和任务消费接口。

这些能力应建立在 1.1 IP 档案稳定、可追溯、可被任务快照引用之后再继续开发。

## 15. 给后续执行会话的操作要求

1. 先完整阅读本方案，再检查当前分支是否存在未提交改动。
2. 只实现本方案的 Phase 1～3，不顺手重写员工、项目和任务列表等无关功能。
3. 如果正式采集清单与本文字段不同，优先保留正式清单的业务含义，并补充映射说明。
4. 任何结构变更都要保持旧扁平字段兼容。
5. 迁移脚本必须支持 dry-run 且幂等。
6. 完成后应记录实际修改文件、数据库迁移命令、构建结果、API 验证结果和跨项目兼容结果。
